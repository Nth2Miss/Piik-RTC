# 共享高负载复测

当前已有多轮首次、再次共享与观看端报告，不要求继续重复下列对照步骤。后续优先由开发侧验证发布生命周期、轨道清理与真实 SDK 运行行为；下列步骤保留作开发排查参考。

## 固定条件

同一共享端、观看端、房间服务商、网络、窗口尺寸、分辨率、帧率和码率下，每次只改变一个因素。观看端最好放在第二台电脑，避免解码也与共享端争抢 GPU。参数在下次开始共享时生效：保存设置后停止、重新共享，并分别导出诊断。

## 首次共享问题的最小复测

当前版本已移除“60fps 均衡强制转为流畅优先”的映射：声网传 `balanced`，即构传 `default`，火山不额外指定 `motion`/`detail` 提示并清除轨道旧提示，交由 SDK 默认策略处理。不同 SDK 的默认策略并不等价，也不保证不降低分辨率或帧率。清晰优先、流畅优先仍保持原选择。新报告中的 `encoderRequest.optimizationMode` 应为 `balanced`；这是应用传参记录，不是 SDK 实测自适应状态。

先关闭 GPU 压测页，PC 共享同一段打斗视频，Pad 观看。固定 1080p60、均衡、手动 8 Mbps，窗口保持可见，轨道路径由程序自动选择。

1. 刷新服务端页面资源后，完全退出桌面客户端（包括托盘），重新打开并进入火山房间。这是冷启动，不能只停止共享代替。
2. 第一次共享 45 秒。异常时保持现场，在停止前从 PC 和 Pad 各导出报告，标记“首次”。记录当时 GPU 各引擎占用。
3. 停止共享，等待 3 秒，在同一房间重新共享同一段视频，保持相同设置。第二次也运行 45 秒，两端各导出报告，标记“再次”。
4. 先分析这四份基线报告。如果基线首次正常，再完全退出客户端、恢复原来的高 GPU 负载，以相同过程复测。不要同时切换策略、码率和负载。

若低负载也出现首次异常、再次恢复，重点比较发布初始化；若低负载正常而高负载异常，继续检查资源压力。此测试用于区分原因，不代表移除设置已修复首次共享问题。

## 没有游戏时

用 Chrome/Edge 打开仓库的 `scripts/gpu-load.html`，点击开始并共享该窗口。可选择平滑图案、战斗、激烈战斗；后两种使用固定种子的细碎场景纹理、镜头快速横移、角色运动、弹道、爆炸、火花，激烈档增加扩散幅度和镜头抖动。每轮 20 秒，前 3 秒和后 3 秒为静态对照，中间 14 秒为战斗；“从头重播”可重复同一段画面。

先固定额外 GPU 工作量为 0，比较平滑与战斗画面，观察高运动对编码分辨率/码率的影响；再固定战斗场景，通过额外的离屏 WebGL 工作逐档增加 GPU 压力。运动画面自身也需要 GPU 运算，因此两项控制独立，但实际 GPU 占用并不完全独立。停止按钮可结束负载。刷新率、浏览器和显卡不同，相同档位不代表相同负载。页面可能触发浏览器 GPU 看门狗；出现上下文丢失时降低档位刷新，不要把它当作 RTC 错误。它是编码压力场景，不等同于真实游戏的渲染管线。

保持测试页在前台，避免浏览器后台节流影响对照。记录任务管理器中实际 GPU 引擎占用；该页面不读取 GPU 占用，也不能完整模拟游戏的显存、复制、驱动和帧调度压力。

## 有游戏时

优先使用游戏自带 Benchmark、固定回放或同一段可重复的打斗。分别测试限制游戏 FPS 与解除限制，或逐档提高画质，使同一显卡出现低、中、高三档实际负载。不要在比较时同时改共享画质与游戏负载。CPU 压力测试不能替代 GPU 压力测试；播放视频主要增加解码负载，也不能等同于游戏 3D 满载。

## 记录方式

1. 任务管理器 → 性能 → GPU，分别观察 3D、Copy、Video Encode、Video Decode（具体项目取决于驱动）；记录负载区间，不能把总占用 98% 直接等同于编码器占用 98%。确认浏览器/WebView2 与游戏使用同一块 GPU。
2. 每个负载档位先稳定 30 秒，再共享 1–2 分钟。先固定 1080p60 与一种优化策略，测试三档负载；再在同一高负载下比较清晰优先、均衡、流畅优先，最后比较 1080p30。
3. 每次共享结束立即导出共享端和观看端报告。`shareAttempts` 保存最近 30 次本机启动尝试，`mediaHistory` 保留最近约 4 分钟；长测试要及时分段导出。
4. 用共享端采样的 `shareId` 找到对应 `shareAttempts[].id`，比较 `requested`、`applied`、`encoderRequest`、采集路径与实际发送分辨率/帧率。`encoderRequest` 是传给 SDK 的参数，不代表 SDK 实测值。观看端自己的设置不是共享端的配置。

每次记录：共享编号、策略、目标帧率、码率上限、采集路径、GPU 各引擎占用、实际发送分辨率与帧率、观看端解码与播放丢帧。采集输入稳定而发送下降时，继续排查轨道消费、编码和发送自适应；只有收到原始受限原因或硬件指标后，才能进一步区分 CPU、GPU 与带宽。

## 编码诊断能力与限制

- 报告版本 3 已加入统一编码诊断。声网可提供编码耗时；即构可提供硬件编码标志与编码帧率；火山可提供编码帧率、编码帧数、编码码率、目标帧率和上行丢包。缺失值使用 `status: unavailable`，真实 0 与 false 保留。
- `qualityLimitationReason` 和编码器实现名称在当前三家公开统计接口中不可得，不能据此报告 CPU 或带宽已经被确认受限。也不能仅凭 H.264 判断硬件加速已启用。
- `observation` 区分 SDK 回调到达、轮询读取和缓存时间；回调超过 6 秒显示过期，SDK 原始采样时间未提供时为 null。重新读取缓存不会更新观测时间；停止共享/取消订阅清理对应缓存。
- 未提供的上行带宽、目标码率、编码耗时不再用缺省 0 导出。编码能力项已明确标不可用；其他可选数值字段会省略，分析旧报告时仍需注意缺省 0。
- 本机 GPU 分引擎占用需原生性能计数器支持，纯网页无法可靠取得；此轮先由任务管理器人工记录。
